Aperture 0.4.7 adds a source-pinned Recipe Lab that translates published inference experiments into capability-gated compatibility records for the hardware Aperture actually observes.

Run the released package without Git:

```powershell
npx.cmd --yes --package=https://github.com/BigBirdReturns/aperture/releases/download/v0.4.7/bigbirdreturns-aperture-0.4.7.tgz aperture recipes --allow-scan
```

On Linux or macOS, use `npx` instead of `npx.cmd`. Node.js 20.11 or newer is required. Distribution remains through GitHub rather than the npm registry namespace.

## What changed

`aperture recipes` performs the existing permissioned local hardware scan and compares it with structured experiment recipes. The first catalog is pinned to `local-inference-lab/rtx6kpro` commit `3023e7c2e572cd445cd62234607aaf765121da58`. Aperture records selected factual observations and exact source coordinates; it does not vendor the upstream prose, scripts, images, Dockerfiles, or executable material.

The first seven records cover Qwen3.8-27B official FP8 TP1 and qualified TP4 profiles, Qwen3.5-397B-A17B NVFP4 TP4, Qwen3.5-122B-A10B NVFP4 TP2, MiniMax-M2.5 NVFP4 TP2, GLM-5 NVFP4 TP2+PP3, and Kimi K2.5 native INT4 TP8.

Each result is `QUALIFIED`, `CANDIDATE`, `UNKNOWN`, or `BLOCKED`. The classification separates hard requirements from source reference conditions. A known numerical floor such as an SM120-class native NVFP4 path can block older observed hardware. A reference 96 GB-class card does not become a fabricated minimum. Approximate source working-set figures remain reference evidence; smaller local hardware is held as `UNKNOWN` until exact checkpoint/context fit or another bounded canary resolves the lower boundary.

Current free VRAM is also separated from physical capability. A machine can remain a hardware candidate while its present headroom is below the source observation. Multi-GPU recipes preserve source GPU count and homogeneous-cohort assumptions rather than treating arbitrary mixed cards as an equivalent tensor-parallel system.

## Hardware observation extension

When the installed NVIDIA driver exposes the fields, the scan now adds compute capability and current PCIe generation/width to the existing capacity observation. The detail probe is additive: failure does not erase the original device, VRAM, or driver inventory. GPU peer-to-peer bandwidth and NUMA locality remain explicitly unmeasured.

The recipe command accepts only `--allow-scan`, `--home`, and `--out`. It does not read model files, contact a model host, download weights, install a runtime, execute inference, stop another workload, or run a benchmark. A recipe classification is compatibility evidence and a next-canary decision, not reproduction of the upstream throughput or quality result.

## Retained capabilities

Release 0.4.7 retains the permissioned support receipt from 0.4.5, the native pre-download GGUF fit gate and physical-capacity split execution from 0.4.4, and exact managed-GGUF cache reuse from 0.4.6. Model inspection, acquisition, runtime installation, and execution keep their existing independent approvals.

## Limits

This release establishes the recipe contract and one seven-record source catalog. It does not claim exhaustive coverage of the upstream wiki, implement vLLM or SGLang distributed serving, pool VRAM, measure GPU peer-to-peer bandwidth, infer NUMA suitability, automatically download the referenced checkpoints, reproduce upstream throughput, validate upstream model quality, or prove that hardware smaller than a reference machine will fit. `QUALIFIED` preserves a source qualification only when the locally observed hard/reference conditions are present; an actual Aperture load and performance canary remains separate.
